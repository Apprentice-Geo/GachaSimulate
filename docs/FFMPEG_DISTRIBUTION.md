# FFmpeg 开发使用与分发状态

## 当前决定

阶段 1–3 使用经过版本和 SHA-256 校验的第三方预编译 FFmpeg 完成内部开发、测试和性能验证。该二进制仅安装到被 Git 忽略的 `build/ffmpeg/win32-x64`，不得进入应用安装包、项目 Release 或其它面向用户的分发产物。

这项决定将技术验证与发布合规拆开：阶段 1–3 可以继续，但其通过只说明 Electron renderer、CDP、PNG 管道和 FFmpeg 宿主行为满足工程契约，不代表 MP4 功能已经具备发布条件。

## 当前开发基线

- 来源：Gyan `ffmpeg 9.0.1 essentials_build` GitHub Release
- 归档：`ffmpeg-9.0.1-essentials_build.zip`
- SHA-256：`fec81ae03971d9dd4be3ebe02e263bd2ec1d789483f931bdba5f5715e65da2e9`
- 对应 FFmpeg 提交：`bf1b838f2a`
- 目标：Windows x64
- 必需能力：`libx264`、PNG `image2pipe` 输入、MP4 输出和 `ffprobe`

`pnpm run prepare:ffmpeg:win` 默认从上述第三方 Release 下载固定归档，也可以通过 `-- -ArchivePath <zip>` 使用本地副本。两种方式都必须通过归档哈希、版本、构建配置和 `libx264` encoder 检查；脚本不接受 PATH 回退。

第三方 essentials build 是包含 `libx264` 及多项外部静态依赖的 GPLv3 build。保存哈希、构建输出和上游链接有助于追溯，但不自动补齐本项目重新分发该二进制时可能承担的对应源码、许可证和声明义务。

## 当前禁止事项

在发布门槛关闭前：

- 不得把 `build/ffmpeg` 加入 `electron-builder.extraResources`、安装包或便携包。
- 不得把当前第三方二进制上传到 GachaSimulate Release，并将其描述为可发布基线。
- 不得把阶段 1–3 集成检查通过描述为许可证或分发合规通过。
- 不得启用依赖该二进制的用户导出入口；桌面 IPC、保存对话框、进度 UI 和用户取消仍属于后续阶段。

Windows CI 可以在临时 runner 中下载并使用该归档进行内部检查。CI 使用结束后 runner 被销毁，不产生应用安装包或长期保存的 FFmpeg 测试产物。

## 解除发布阻塞

满足以下任一决策路径后，才能考虑把 FFmpeg 接入安装包和应用发布。

### 路径 A：项目自行编译

优先选择只启用导出所需组件的最小 Windows x64 build，并至少完成：

- 固定 FFmpeg、x264 和实际参与构建的其它外部依赖版本及源码哈希。
- 提交可复用构建脚本、工具链版本、配置参数和项目补丁。
- 为每个发布二进制生成可以精确对应的源码与许可证材料，并提供清晰下载入口。
- 复核最终 `-version`、`-buildconf`、`-encoders` 和依赖清单。
- 使用最终自编译 build 重跑阶段 1–3 集成检查、性能与背压基线，再完成安装包断网验证。
- 由维护者复核项目许可证、FFmpeg/x264 义务以及必要声明。

材料可以合并为少量归档，不要求沿用特定文件名；关键是内容完整、版本精确且能从发布二进制追溯到对应源码和构建方式。

### 路径 B：维护者明确接受第三方分发风险

维护者需要针对最终选定的二进制和发布方式作出书面决定，记录已知缺口、缓解措施和复核范围，然后再修改打包配置。接受风险只是项目决策，不会消除许可证义务，也不能被描述为已经合规。

## 重新评审触发条件

FFmpeg 版本、构建来源、encoder、链接方式、外部依赖、项目许可证、目标平台或安装包内容发生变化时，必须重新评审本文件。发布门槛的最终状态应同时更新 `ELECTRON_EXPORT_PLAN.md`、打包配置和开发检查文档。
