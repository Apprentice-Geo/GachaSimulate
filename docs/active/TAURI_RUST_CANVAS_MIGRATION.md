# Tauri、Rust 与 Canvas 迁移设计

目标平台为 Windows x64。主仓库用 Rust 实现 YAML 编译、模拟、结果分析和 Tauri 桌面宿主，用 React 与 TypeScript 维护工作台和 Canvas 画面。配置仓库的打包、校验和 CI 一起迁到 Rust。交付分三步，桌面迁移是内部里程碑，Canvas 展示和真实文件导出通过验收后才发布完整版本。

## 里程碑与交付条件

| 里程碑 | 可运行的交付物 | 验收 |
| --- | --- | --- |
| 1．计算核心与配置仓库 | Rust 能从一份 YAML 快照编译并执行模拟、保存结果、重新打开并生成统计。配置仓库能用 Cargo 生成发布包。 | 正式配置的每个终止条件均可编译。确定性样例的库存与原因正确，随机样例可按 run 序号复现。Ubuntu CI 重建的包在 Windows 上通过 Rust 库校验并能启动计算。 |
| 2．Tauri 工作台 | Windows 安装包提供配置安装、本地配置、模拟、取消、打开结果及结果目录。阶段内隐藏可视化、原位编辑与导出入口。 | 从安装包完成一次真实模拟，重启后能打开新结果。在编译、计算、写盘期间取消或关闭应用，已取消任务无法提交结果，工作进程得到回收。 |

## Gemini 主 Agent 的调度方式

主仓库集成分支为 `refactor/tauri-rust-canvas`。Gemini 主 Agent 在该分支管理任务依赖、接口决定、共享构建文件和合并顺序。每个可并行任务可使用从集成分支分出的短期分支或独立 worktree，回收到同一集成分支。配置仓库在执行打包迁移时另开配套分支，由主 Agent 记录对应的主仓库提交。跨仓库固定依赖前，确认该提交在配置仓库 CI 可获取。

- **Gemini 主 Agent** 给每位执行者指定下表中的任务、输入样例、负责目录和验收项。共享接口有变化时，更新生产者与消费者共用的样例，通知受影响的任务负责人。每次集成记录提交、通过的检查和还在使用替身的入口。
- **Codex 执行者**负责规则语义、结果格式与统计、并发、进程生命周期及导出传输等高复杂度实现。**Codex 审查者**从另一上下文审查实现与样例，关注输入边界、数值精度、资源上限、取消和文件提交时序。作者修复后由主 Agent 集成。前端任务也由 Codex 审查跨层契约与状态行为，Gemini 在真实界面上验收布局和交互。
- 工作表中的编号可直接用于派单。“可开始”列给出最早开工条件；可以用固定样例开工的任务，须在当阶段换成真实生产者做最后一次验收。共享的 workspace 成员表、锁文件、顶层 CI 和桌面命令注册由主 Agent 统合，模块内代码和测试归各任务负责人。

**兼容策略。** 设计按全新安装和新格式验收。旧 GSR、sidecar、seed 序列、CLI、IPC、旧版安装升级和数据目录迁移均没有兼容交付项。涉及破坏性改动时，在同一里程碑更新受影响的生产方、消费方和正式配置。仍有价值的规则语义、统计含义和用户编辑行为由行为样例保护。旧数据留在原处。

### 编译和打包

主仓库维护可脱离 Tauri 构建的配置编译库、配置分发协议和计算核心。编译器从内存中的 YAML 文件集合构造有类型的程序，运行时直接执行。JSON IR、临时 program.json 和按旧 JSON 形状重新校验的 loader 可随 C++ 退出。桌面安装、手动选择和启动模拟均依据读取到的完整快照校验，执行期间不再按文件名重读 YAML。外部文件、下载包和跨进程请求仍在各自入口校验。[当前 IR 边界](../IR.md) · [配置协议](../CONFIG_REPOSITORY.md)

配置仓库拥有轻量 Rust 打包程序，通过 Cargo 的 Git 修订号引用主仓库的编译与协议库，提交自己的 Cargo.lock。打包程序负责读取目录、验证全部 termination、生成 ZIP、计算 SHA-256 和写 index；桌面端负责下载、摘要校验与安装提交。配置仓库不需要构建 Tauri 或安装 Node/pnpm。配置作者继续用 YAML，已有 index 和包布局可直接沿用。[配置仓库现有构建入口](https://github.com/Apprentice-Geo/GachaSimulate-Configs/blob/main/scripts/build_repository.ts)

打包时把每个配置包的文件读为一份快照。校验和写 ZIP 都使用其中的同一批字节，避免校验结束后再次从磁盘读出已改动的文件。用正式 YAML 全量重建到暂存目录，验证后一起更新 dist 和 CI。固定文件顺序、时间戳和 ZIP 属性，检验同一提交连续两次构建的产物字节一致。更换压缩实现可能一次性改变 ZIP 摘要，index 要与这批 ZIP 同次发布。检查 dist 时覆盖过期文件和未跟踪文件。

### 哪些结果必须一致

- **规则语义**沿用现有 YAML 的执行顺序。重点移植同步抽取与即时分解、条件命中后收集动作、OR 短路、repeat 可退出性、终止后的动作截断，以及每 run 的 step 和深度上限。用可手算的例子核对库存与原因，辅以现有语义和非法输入样例。[YAML 配置语义](../YAML_CONFIG_SYNTAX.md)
- **新引擎的随机性**以全局种子和 run 序号派生每次模拟的随机流。明确固定随机算法、种子派生与均匀数到累计概率区间的映射，保留测试向量。改变线程数、分块、执行顺序或增加总次数，已有序号应得到相同结果。跨 C++ 和 Rust 的正确性用已知概率、阈值边界和确定性规则检验。旧种子逐次重放不在兼容目标内。
- **统计口径**保留百分位插值后取整、均值所在累计水平、终止原因按余数分配百分比等用户可见含义。以手工构造的观测值验证整数边界、相同余数及单点分布。Rust 端用整数精确统计，跨到 JS 的大整数使用十进制字符串，显示完整数值；绘图坐标由独立的比例换算产生，避免合法结果因累计总量超出 JS 安全整数范围而打不开。[现有统计定义](../ANALYSIS.md)

### 结果文件与大任务

每个 run 保留期末库存和终止原因，以后改变统计口径时仍可重新分析结果。采用可顺序写入的分块 GSR 布局，提前从编译后的程序确定原因表。每块标明起始 run 序号与条数，记录配对的库存值和原因索引。调度器限制同时计算及等待写出的块总数；若早期块特别慢，窗口满后暂停派发新块，按序写入临时文件。用慢首块测试验证内存上界。当前实现在接近十亿 run 时仅两组结果数组就需要约 12 GB，这是改布局的主要收益。[现有批量分配](../../cpp/src/runtime.cpp) · [现有 GSR 布局](../GSR.md)

首个实现先冻结新格式的标识、字节序、计数、长度与总量校验，并保留固定二进制样例。读取时拒绝缺块、重复序号、越界引用、截断和算术溢出。分析可逐块累积频数与原因计数；大量不同库存值仍会占用内存，需保留分析输出大小限制，用高基数样例单独测试。原始结果和用户编辑的展示字段分别保存，改标题或单位只原子替换对应的 sidecar。[展示字段的现有职责](../DISPLAY_CONFIG.md)

### 宿主与前端的职责

React 工作台通过有限的业务命令请求操作。Tauri 宿主持有系统对话框、路径、任务标识、当前结果会话和输出提交权。前端按配置 ID 启动模拟、按会话 ID 保存或导出，宿主核验来源窗口和任务状态。模拟工作进程只接收选项、配置快照和宿主分配的临时输出；长时间模拟和大型结果分析均可由同一款 Rust 工作程序的对应子命令执行。进度按任务标识发送，宿主等待进程成功结束并核验输出后才提交。保留独立进程的成本是一个受控的消息接口，收益是遇到长任务或工作进程故障时桌面仍能取消并回收资源。[现有任务与退出契约](../../ARCHITECTURE.md)

取消的决定由宿主记录。先请求协作停止，超时后终止进程并等待退出；结束前屏蔽迟到的进度和成功消息。取消、错误和磁盘写满均关闭并清理本次临时输出，已提交文件保留。清理失败时保留任务所有权和可重试入口。配置安装也使用暂存目录与最终提交，避免失败更新破坏当前可用配置。

简化当前跨层重复处理取消的逻辑。由宿主按任务 ID 维护唯一的任务状态，并为状态更新分配递增序号。前端发出取消请求时冻结当前读数，收到确认后按新状态显示；重进页面时从宿主读取快照，忽略旧任务或已过期的事件。用“取消与成功同时到达”和“切页后收到上一个任务的进度”两个场景验证。

每次打开结果只分析一次。前端从已校验的 Analysis 建立一次曲线数据，通过确认可展示后再切换当前会话；失败可继续使用上次结果。侧栏设置、草稿和保存队列属于工作台。导出等待保存完成，固定会话、曲线数据引用和已保存展示字段；用户随后编辑或切页不会改变这次已接受的任务。这样宿主无需构建第二份前端曲线模型。

## 阶段三 · Canvas 展示与像素导出

### 首项实验 · 随包 FFmpeg 与 4K 帧传输

**先解决已知阻塞。** 当前随包 FFmpeg 为视频帧启用的是 PNG 输入。Gemini 负责调整现有构建脚本，启用 rawvideo 解复用和解码，更新能力检查和发布材料。用该脚本产出的 FFmpeg 将一帧已知 RGBA 输入编码为 H.264，并解码核查画面。保留现有 libx264、H.264 和 yuv420p 输出路径。[FFmpeg 构建脚本](../../scripts/build_ffmpeg_win_ucrt64.sh)

**同时测量像素传输成本。** Gemini 前端执行者制作带帧号标记的简单 Canvas，Codex 负责二进制传输、背压和计时。两端先约定尺寸、RGBA 顺序、帧号与接收确认。待编码器就绪，在目标 Windows 机器跑通 3840 × 2160、60 帧的完整链路。单帧约 31.6 MiB，全段约 1.85 GiB。分别记录绘制、读回、传输、编码、总耗时和峰值内存，同时检查帧序、编码参数以及中途取消能否回收进程。60 FPS 是成品播放帧率，离线生成允许耗时超过一秒。

Gemini 主 Agent 记录使用的安装包、机器和测量结果，Codex 审查读数与资源释放。帧正确、有界传输和取消通过后，采用该传输路径；若耗时主要来自跨进程传输且影响导出体验，再由 Codex 对照测量 Windows 共享缓冲区。若瓶颈在绘制、读回或编码，优先处理对应环节。完成这次实验后再分派正式画面与导出任务。

### 共享画面与成品验收

采用一套以设计坐标绘制的 Canvas 2D 场景。输入为已准备的曲线数据、展示字段、布局和动画时间，输出覆盖页头、曲线、marker、统计栏、路径条和说明。图表预览可单独绘制其中的 CDF 区域。预览和正式页面按可用空间显示，导出使用独立的固定尺寸 Canvas。等待随包字体加载，再计算字宽、基线、marker 边界和省略号。编辑模式停在终态，React 根据同一布局给出的字段矩形放置输入框，负责中文输入法、键盘、焦点与失焦保存。工作台导航和输入控件留在画面外。[视觉与交互要求](../VISUALIZATION_DESIGN.md)

逐帧导出按帧号计算动画时间。PNG 直接编码第 57 帧的 Canvas 位图。视频逐帧读取 RGBA，经 Tauri 二进制请求交给 Rust，再写入 FFmpeg 标准输入，使用明确的像素格式、尺寸和帧率编码。每次只允许一帧在途，接收方检查任务标识、帧号和字节数，等待写入完成才放行下一帧；消费变慢时绘制自然暂停。双格式导出复用同一终态画面。输出继续使用每文件独立提交，复核覆盖目标，保留已成功提交的文件。[Tauri 原始请求体](https://v2.tauri.app/develop/calling-rust/) · [FFmpeg rawvideo](https://ffmpeg.org/ffmpeg-formats.html#rawvideo)

用 ffprobe 检查画幅、编码、60 FPS 和 60 帧，用可识别的测试画面检查帧序。在送入编码器前检查第 57–59 帧的终态像素一致，并与解码后的静态 PNG 对照。H.264 有损编码后的颜色另做解码检查。[现有导出集成检查](../../src/dev/export_host_integration.ts)

## 发布与旧实现退场

第一阶段保留现有引擎用于规则对照和性能基线。相同机器、相同配置和固定 run 数下记录批量模拟耗时、峰值内存与输出大小，同时记录实际总结果以解释随机工作量差异。第二阶段将 Windows 打包和应用测试切到 Tauri，验证全新安装、WebView2 安装、工作进程与字体定位。Rust 工具链纳入 CI，FFmpeg 的 UCRT64 构建与材料收集继续保留。第三阶段用安装包内的 FFmpeg 完成端到端导出，在预览和导出中检查中文长标题、极端数值、单点 CDF 以及重叠 marker。

按里程碑替换对应旧测试。计算和配置覆盖齐备后退役 C++ 和 TS 编译器；Tauri 接管后移除 Electron 主进程、preload 与旧打包链；原截图样例可留作视觉参考。Canvas 导出验收覆盖现有用户行为后清除隐藏窗口、CDP 截图和 PNG 视频输入的专用代码与检查。相应里程碑落地时同步更新架构、格式和开发文档，并在发布说明中写明新结果格式的兼容范围。
