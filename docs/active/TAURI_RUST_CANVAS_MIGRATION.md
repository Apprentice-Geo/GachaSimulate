# Tauri、Rust 与 Canvas 迁移设计

目标平台为 Windows x64。主仓库用 Rust 实现 YAML 编译、模拟、结果分析和 Tauri 桌面宿主，用 React 与 TypeScript 维护工作台和 Canvas 画面。配置仓库的打包、校验和 CI 一起迁到 Rust。交付分三步，桌面迁移是内部里程碑，Canvas 展示和真实文件导出通过验收后才发布完整版本。

本次迁移的开发、构建、性能测量和安装包验收均在同一台 Windows x64 开发机上完成。配置仓库的 Ubuntu CI 和主仓库的 Windows CI 继续执行各自的自动化检查。

## 迁移起点（2026-11-27）

主仓库基线为 `v0.3.2`（`7214d2d`）。该版本已支持模拟完成后直接查看结果、预览 CDF、原位编辑展示字段和跟随系统主题。桌面端仍使用 Electron，YAML 由 TypeScript 编译，模拟与分析由 C++ 执行。可按[开发检查](../DEVELOPMENT_CHECKS.md)复测此基线。

截至 `5b971d0`，集成分支相对基线仅增加了迁移设计。阶段一待集成的首项是 1A 的 Cargo workspace 和契约样例。配套配置仓库的本地基线为 `475b037`，仍使用 TypeScript 打包，并通过 `GACHASIMULATE_COMMIT` 固定主仓库的 `v0.3.1`（`f3adf33`）编译器。

本机已复测 Electron 基线的模拟与结果会话、CDF、两种窗口尺寸的布局和真实 PNG／MP4 导出。导出集成检查通过了帧序、终态、取消及异常退出清理断言，随后已恢复普通生产构建。

## Gemini 主 Agent 的调度方式

主仓库集成分支为 `refactor/tauri-rust-canvas`。Gemini 主 Agent 在该分支管理任务依赖、接口决定、共享构建文件和合并顺序。每个可并行任务可使用从集成分支分出的短期分支或独立 worktree，回收到同一集成分支。配置仓库在执行打包迁移时另开配套分支，由主 Agent 记录对应的主仓库提交。跨仓库固定依赖前，确认该提交在配置仓库 CI 可获取。

- **Gemini 主 Agent** 派单时注明基线提交、负责目录、共用接口和验收样例，维护 workspace 成员表、锁文件、顶层 CI 和桌面命令注册。接口变化由主 Agent 协调双方更新同一份样例。各分支通过表中列出的独立检查即可提交审查，真实生产者与消费者的联调分别归 1F、2E、3E。
- **Gemini 执行者**负责全部 UI 设计与实现，包括工作台和 Canvas 的布局、视觉、交互与动效。Gemini 按既定场景运行应用、采集截图与操作结果，并负责需要设计判断的修订。
- **Codex 执行者（GPT-6.2-Sol-High）**负责计算、存储、进程、命令与传输协议。**所有独立审查与里程碑验收结论均由另一上下文的 Codex 审查者负责**，包括代码、接口、测试和安装包证据。对于 UI，审查者依据既定设计与行为要求报告偏差及复现条件，由 Gemini 决定具体设计和修复方式。作者完成修复、Codex 复核后，由 Gemini 主 Agent 合并并记录提交与尚待联调的入口。

**兼容策略。** 设计按全新安装和新格式验收。旧 GSR、sidecar、seed 序列、CLI、IPC、旧版安装升级和数据目录迁移均没有兼容交付项。涉及破坏性改动时，在同一里程碑更新受影响的生产方、消费方和正式配置。仍有价值的规则语义、统计含义和用户编辑行为由行为样例保护。旧数据留在原处。

### 1G 性能测量与结果记录

沿用上次迁移的三个配置 `baseline_probability`、`condition_tree_rules`、`weighted_pool`，分别测量 100、10,000 和 1,000,000 runs。两端使用开发机上的 Release 构建、同一份配置与 termination、相同统计物品、种子 123 和线程数（单线程与 16 线程）。三个规模分别独立运行 7、5、3 次，报告中位数与范围。上次报告在 WSL2 上采样，本次从迁移前的固定提交重新构建 C++ 基线，保留修订号与复测命令，以便旧实现退场后仍能复测。[Python → C++ 性能报告](../archived/CPP_PYTHON_PERFORMANCE_BASELINE.md)

两端都从编译好的程序就绪后开始计时，到完整批量模拟并写完 GSR 为止；另计从重新打开该 GSR 到写完 Analysis JSON 的耗时。按配置、规模和线程数并列记录两端耗时、耗时比（C++ / Rust）、峰值内存（统一采样模拟或分析进程的 Windows 工作集）、GSR 字节数和实际 `total_result`。小规模结果用于观察固定开销，百万 runs 用于比较持续吞吐。各 agent 可并行开发，性能采样与本机的全量编译、4K 编码等高负载任务错开。

测完将实测表、开发机配置与工具链版本、两端提交、运行命令和差异说明写入 `docs/archived/CPP_RUST_PERFORMANCE_BASELINE.md`，并在本节补上报告链接。[C++ / Rust 性能报告](../archived/CPP_RUST_PERFORMANCE_BASELINE.md)解释结果时注明两端的随机流和 GSR 布局差异。

### 编译和打包

主仓库维护可脱离 Tauri 构建的配置编译库、配置分发协议和计算核心。编译器从内存中的 YAML 文件集合构造有类型的程序，运行时直接执行。JSON IR、临时 program.json 和按旧 JSON 形状重新校验的 loader 可随 C++ 退出。桌面安装、手动选择和启动模拟均依据读取到的完整快照校验，执行期间不再按文件名重读 YAML。外部文件、下载包和跨进程请求仍在各自入口校验。[当前 IR 边界](../IR.md) · [配置协议](../CONFIG_REPOSITORY.md)

配置仓库拥有轻量 Rust 打包程序，通过 Cargo 的 Git 修订号引用主仓库的编译与协议库，提交自己的 Cargo.lock。打包程序负责读取目录、验证全部 termination、生成 ZIP、计算 SHA-256 和写 index；桌面端负责下载、摘要校验与安装提交。配置仓库不需要构建 Tauri 或安装 Node/pnpm。配置作者继续用 YAML，已有 index 和包布局可直接沿用。[配置仓库现有构建入口](https://github.com/Apprentice-Geo/GachaSimulate-Configs/blob/main/scripts/build_repository.ts)

打包时把每个配置包的文件读为一份快照。校验和写 ZIP 都使用其中的同一批字节，避免校验结束后再次从磁盘读出已改动的文件。用正式 YAML 全量重建到暂存目录，验证后一起更新 dist 和 CI。固定文件顺序、时间戳和 ZIP 属性，检验同一提交连续两次构建的产物字节一致。更换压缩实现可能一次性改变 ZIP 摘要，index 要与这批 ZIP 同次发布。检查 dist 时覆盖过期文件和未跟踪文件。

### 哪些结果必须一致

- **规则语义**沿用现有 YAML 的执行顺序。重点移植同步抽取与即时分解、条件命中后收集动作、OR 短路、repeat 可退出性、终止后的动作截断，以及每 run 的 step 和深度上限。用可手算的例子核对库存与原因，辅以现有语义和非法输入样例。[YAML 配置语义](../YAML_CONFIG_SYNTAX.md)
- **新引擎的随机性**以全局种子和 run 序号派生每次模拟的随机流。明确固定随机算法、种子派生与均匀数到累计概率区间的映射，保留测试向量。改变线程数、分块、执行顺序或增加总次数，已有序号应得到相同结果。跨 C++ 和 Rust 的正确性用已知概率、阈值边界和确定性规则检验。旧种子逐次重放不在兼容目标内。
- **统计口径**保留百分位插值后取整、均值所在累计水平、终止原因按余数分配百分比等用户可见含义。以手工构造的观测值验证整数边界、相同余数及单点分布。Rust 端用整数精确统计，跨到 JS 的大整数使用十进制字符串，显示完整数值；绘图坐标由独立的比例换算产生，避免合法结果因累计总量超出 JS 安全整数范围而打不开。[现有统计定义](../ANALYSIS.md)

### 结果文件与大任务

每个 run 保留期末库存和终止原因，以后改变统计口径时仍可重新分析结果。采用可顺序写入的分块 GSR 布局，提前从编译后的程序确定原因表。每块标明起始 run 序号与条数，记录配对的库存值和原因索引。调度器限制同时计算及等待写出的块总数；若早期块特别慢，窗口满后暂停派发新块，按序写入临时文件。用慢首块测试验证内存上界。当前实现在接近十亿 run 时仅两组结果数组就需要约 12 GB，这是改布局的主要收益。[现有批量分配](../../cpp/src/runtime.cpp) · [现有 GSR 布局](../GSR.md)

首个实现先冻结新格式的标识、字节序、计数、长度与总量校验，并保留固定二进制样例。读取时拒绝缺块、重复序号、越界引用、截断和算术溢出。分析器逐块累积频数与原因计数。每遇到新的库存值就更新紧凑 JSON 字节数的保守下界，一旦下界超过 64 MiB 即停止读取，序列化时再检查实际大小。1D 用高基数输入验证超限时提前停止，并用接近上限的合法输出验证不会误拒。GSR 保存原始结果，展示字段单独保存在 sidecar 中。[现有分析器](../../cpp/src/result.cpp) · [展示字段契约](../DISPLAY_CONFIG.md)

### 宿主与前端的职责

React 工作台通过有限的业务命令请求操作。模拟请求携带配置来源（`installed` 或 `local`）、配置 ID、termination 文件名、result item、run 数、种子和线程数。2C 按来源和 ID 读取一次完整快照，2B 使用这份快照校验所选 termination 和物品并启动工作进程。宿主持有系统对话框、路径、任务标识、当前结果会话和输出提交权，按来源窗口、任务状态和会话 ID 核验请求。工作进程接收选项、配置快照和宿主分配的临时输出，通过独立子命令执行模拟或大型结果分析。宿主按任务标识发送进度，等待进程成功结束并核验输出后提交。[配置选择行为](../../src/main/config_manager.test.ts) · [任务与退出契约](../../ARCHITECTURE.md)

取消的决定由宿主记录。先请求协作停止，超时后终止进程并等待退出；结束前屏蔽迟到的进度和成功消息。取消、错误和磁盘写满均关闭并清理本次临时输出，已提交文件保留。清理失败时保留任务所有权和可重试入口。配置安装也使用暂存目录与最终提交，避免失败更新破坏当前可用配置。

简化当前跨层重复处理取消的逻辑。由宿主按任务 ID 维护唯一的任务状态，并为状态更新分配递增序号。前端发出取消请求时冻结当前读数，收到确认后按新状态显示；重进页面时从宿主读取快照，忽略旧任务或已过期的事件。用“取消与成功同时到达”和“切页后收到上一个任务的进度”两个场景验证。

每次打开结果只分析一次。宿主返回候选会话，前端从已校验的 Analysis 建立曲线数据，保留精确整数用于读数与比较，单独换算绘图坐标。前端按候选会话 ID 确认可展示后，宿主才切换当前会话。建模失败或确认已过期时保留当前有效结果。阶段二用结果摘要验证大整数，阶段三复用同一模型绘图。

工作台维护侧栏设置、草稿和保存队列。2B 在写入和提交 sidecar 时保证保存请求仍属于目标会话，原子替换成功后返回会话 ID 与已保存字段。3D 在保存失败时保留草稿，提供重试与放弃操作。导出等待保存队列完成后固定会话、曲线数据引用和已保存字段，后续编辑或切页均沿用已接受的导出快照。[展示字段与保存行为](../DISPLAY_CONFIG.md)

## 阶段三 · Canvas 展示与像素导出

### 首项实验 · 随包 FFmpeg 与 4K 帧传输

当前随包 FFmpeg 为视频帧启用的是 PNG 输入。Gemini 可从迁移开始就调整构建脚本，启用 rawvideo 解复用和解码，更新能力检查和发布材料。用该脚本产出的 FFmpeg 将一帧已知 RGBA 输入编码为 H.264/yuv420p。在开发机上用另一份支持 RGBA 原始帧输出的 FFmpeg 解码取像素，并记录其版本。成品编码始终使用随包二进制。[FFmpeg 构建脚本](../../scripts/build_ffmpeg_win_ucrt64.sh)

**同时测量像素传输成本。** Gemini 前端执行者制作带帧号标记的简单 Canvas，Codex 负责二进制传输、背压和计时。两端先约定尺寸、RGBA 顺序、帧号与接收确认。待编码器就绪，在开发机上跑通 3840 × 2160、60 帧的完整链路。单帧约 31.6 MiB，全段约 1.85 GiB。分别记录绘制、读回、传输、编码、总耗时和峰值内存，同时检查帧序、编码参数以及中途取消能否回收进程。60 FPS 是成品播放帧率，离线生成允许耗时超过一秒。

2E 的 Tauri 壳可安装后即可测量传输。Gemini 主 Agent 记录安装包版本、开发机配置和测量结果，Codex 独立审查帧正确性、资源上界与取消结果。若跨进程传输成为主要瓶颈并影响导出体验，Codex 对照测量 Windows 共享缓冲区。3A 的结论决定 3C 采用的传输方式；3B 可在此期间开发画面。

### 共享画面与成品验收

采用一套以设计坐标绘制的 Canvas 2D 场景。输入为已准备的曲线数据、展示字段、布局和动画时间，输出覆盖页头、曲线、marker、统计栏、路径条和说明。图表预览可单独绘制其中的 CDF 区域。预览和正式页面按可用空间显示，导出使用独立的固定尺寸 Canvas。等待随包字体加载，再计算字宽、基线、marker 边界和省略号。编辑模式停在终态，React 根据同一布局给出的字段矩形放置输入框，负责中文输入法、键盘、焦点与失焦保存。工作台导航和输入控件留在画面外。[视觉与交互要求](../VISUALIZATION_DESIGN.md)

3D 在任务接受时为导出快照持有独立 Canvas，按帧号计算动画时间并调用共享画面入口。单独导出 PNG 时直接绘制第 57 帧并编码位图。视频按顺序读取 RGBA，经 3A 选定的传输方式交给 3C 写入 FFmpeg 标准输入，显式指定像素格式、尺寸与帧率。每次只允许一帧在途，3C 检查任务标识、帧号和字节数，写入完成后确认，3D 收到确认才绘制下一帧。取消或失败时结束等待并释放 Canvas 与编码进程。双格式任务从同一次绘制的第 57 帧取得 PNG 和视频输入，每个文件分别复核覆盖目标并提交，保留已成功提交的文件。[Tauri 原始请求体](https://v2.tauri.app/develop/calling-rust/) · [FFmpeg rawvideo](https://ffmpeg.org/ffmpeg-formats.html#rawvideo)

用 ffprobe 检查画幅、编码、60 FPS 和 60 帧。帧序测试解码带帧号标记的视频，按播放顺序读回标记。终态测试使用无标记的正式画面，在送入编码器前逐像素比较第 57–59 帧，并与解码后的 PNG 对照。H.264 成品另做允许有损色差的画面检查。[现有导出集成检查](../../src/dev/export_host_integration.ts)

## 发布与旧实现退场

第一阶段保留现有引擎用于规则对照。第二阶段将 Windows 打包和应用测试切到 Tauri，验证全新安装、WebView2 安装、工作进程与字体定位。Rust 工具链纳入 CI，FFmpeg 的 UCRT64 构建与材料收集继续保留。第三阶段用安装包内的 FFmpeg 完成端到端导出，在预览和导出中检查中文长标题、极端数值、单点 CDF 以及重叠 marker。

按里程碑替换对应旧测试。阶段一保留现有桌面入口所需的 C++ 和 TS 编译器，待 1F 留存对照数据、配置仓库已固定 Rust 库且 2E 接管安装与模拟后，再移除旧计算链、Electron 主进程、preload 与旧打包链。提前留存导出帧和交互样例供阶段三对照。Canvas 导出验收覆盖现有用户行为后清除剩余的隐藏窗口、CDP 截图和 PNG 视频输入专用代码与检查。相应里程碑落地时同步更新架构、格式和开发文档，并在发布说明中写明新结果格式的兼容范围。
